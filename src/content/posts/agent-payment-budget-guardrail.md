회사에서 법인카드는 묘한 물건입니다. 한 장의 플라스틱 카드처럼 보이지만, 그 안에는 보이지 않는 규칙이 빽빽하게 들어 있습니다. 누가 쓸 수 있는지, 얼마까지 쓸 수 있는지, 어떤 항목은 안 되는지, 영수증은 언제까지 붙여야 하는지, 결재선은 어디까지 올라가는지. 카드를 건네받는다는 것은 돈을 받는 일이 아니라, 조직의 신뢰와 제한을 함께 받는 일에 가깝습니다.

그래서 대기업의 지출은 늘 속도와 통제 사이에 있습니다. 출장 중 급히 결제해야 하는 구독형 데이터가 있고, 프로젝트 검토를 위해 잠깐 써야 하는 유료 리포트가 있습니다. 매번 사람에게 물으면 일은 멈춥니다. 반대로 아무 제한 없이 열어두면 예산과 보안은 금세 불안해집니다. 업무 자동화가 깊어질수록 이 질문은 더 날카로워집니다. “AI가 대신 일한다면, AI는 어디까지 돈을 써도 되는가.”

이 질문을 정면으로 다룬 기술 글이 나왔습니다. AWS와 OpenClaw Foundation은 2026년 8월 17일 AWS Machine Learning Blog에 `Amazon Bedrock AgentCore payments`를 이용해 OpenClaw 에이전트가 유료 API나 콘텐츠 접근 과정에서 HTTP 402 Payment Required 응답을 처리하는 방식을 소개했습니다. 글의 핵심은 에이전트에게 지갑 비밀번호를 통째로 넘기는 것이 아닙니다. 사람이 미리 승인한 수신자, 자산, 네트워크, 건별 한도, 누적 예산, 만료시간 안에서만 에이전트가 결제를 시작할 수 있게 하는 구조입니다. 법인카드를 건네되, 카드 한도와 사용처와 회수 시간을 시스템으로 박아두는 셈입니다.

## ▸ 결제창이 자동화의 중간에 나타나는 순간 : 멈춤과 통과 사이

AWS 글은 자율 에이전트가 웹을 탐색하고, API를 호출하고, MCP 서버를 질의하는 과정에서 유료 서비스의 `HTTP 402 Payment Required` 응답을 만날 수 있다고 설명합니다. 사람이 매번 옆에 앉아 결제를 승인하지 않아도 업무가 이어지려면, 에이전트에게 어떤 결제 경로가 필요합니다. 다만 그 경로는 사전에 승인된 제한 안에서만 작동해야 합니다.

이 지점이 중요합니다. 지금까지 많은 업무 자동화는 ‘무료로 접근 가능한 내부 데이터’나 ‘이미 로그인된 SaaS’ 안에서 상상되었습니다. 그러나 에이전트가 실제 업무를 맡기 시작하면 바깥의 유료 API, 종량제 데이터 피드, 유료 콘텐츠, 미터링된 MCP 도구를 만날 가능성이 커집니다. 시장 데이터 한 건, 신용정보 조회 한 번, 전문 리포트 일부, 외부 계산 API 호출처럼 작지만 반복되는 결제가 업무 흐름 안으로 들어옵니다.

AWS는 이 구현 예시에서 AgentCore payments가 지갑 연동, 지출 한도, 결제 오케스트레이션을 제공한다고 설명합니다. x402나 Machine Payments Protocol 같은 프로토콜은 에이전트와 서비스 사이의 프로그램 가능한 결제 흐름을 뒷받침하는 방향으로 언급됩니다. 이 글은 특정 프로토콜 하나의 승리를 선언하는 글이라기보다, 에이전트가 ‘읽고 쓰는’ 단계를 넘어 ‘거래하는’ 단계로 갈 때 어떤 안전장치가 필요한지를 보여주는 사례에 가깝습니다.

## ▸ 숨은 구조는 지갑이 아니라 권한의 분리다

겉으로 보면 이 뉴스는 AI 에이전트 결제 기능처럼 보입니다. 하지만 기업 업무 관점에서 더 중요한 단어는 결제보다 분리입니다. AWS 글은 안전한 설계가 지갑 제공자 자격증명과 결제 세션을 만들거나 확장할 권한을 모델이 직접 보는 런타임 밖에 둔다고 설명합니다. 에이전트는 승인된 세션 안에서 결제를 시작할 수 있지만, 새 세션을 만들거나 한도를 늘리거나 다른 지갑으로 바꾸는 권한은 갖지 않습니다.

이것은 대기업 업무의 오래된 원칙과 닮아 있습니다. 실무자가 비용을 집행할 수는 있지만 예산 계정을 마음대로 만들 수는 없습니다. 담당자가 외부 업체에 견적을 요청할 수는 있지만 계약 조건을 임의로 바꿀 수는 없습니다. 업무 권한과 관리 권한은 다릅니다. 에이전트 시대에도 이 구분은 사라지지 않습니다. 오히려 더 명시적으로 시스템에 들어가야 합니다.

특히 AWS 글은 프롬프트 인젝션을 막는다고 단정하지 않습니다. 대신 신뢰할 수 없는 입력이 모델을 조작할 수 있다고 가정하고, 런타임의 권한을 수신자, 자산, 네트워크, 건별 결제액, 세션 예산, 만료시간으로 제한한다고 설명합니다. 이것이 흥미로운 대목입니다. 안전의 출발점이 “모델이 절대 속지 않을 것”이라는 믿음이 아니라, “모델이 속더라도 쓸 수 있는 돈과 갈 수 있는 곳을 좁힌다”는 운영 설계에 있기 때문입니다.

## ▸ 효율인가 위험인가 : 같은 자동 결제의 두 얼굴

에이전트 결제는 분명히 효율을 만듭니다. 장기 실행형 리서치 에이전트가 밤새 경쟁사 자료를 모으다가 유료 데이터 포인트 하나를 만나면, 사람을 깨우지 않고도 사전에 정한 한도 안에서 작업을 계속할 수 있습니다. 고객 지원 에이전트가 외부 검증 API를 호출하거나, 구매 분석 에이전트가 종량제 가격 데이터를 조회하는 장면도 상상할 수 있습니다. 자동화가 사람의 대기 시간에 묶이지 않는다는 점에서 업무 리드타임은 줄어듭니다.

하지만 돈을 쓰는 자동화는 일반적인 문서 요약 자동화보다 위험의 성격이 다릅니다. 잘못된 요약은 고치면 되지만, 잘못된 결제는 비용과 계약과 감사의 문제로 번집니다. 특히 유료 콘텐츠나 API 응답은 다시 에이전트의 다음 판단 재료가 될 수 있습니다. AWS 글도 유료 응답을 받을 때 그것을 지시가 아니라 데이터로 다뤄야 한다는 취지의 주의를 둡니다. 결제된 콘텐츠가 다시 모델을 조작하는 통로가 될 수 있기 때문입니다.

따라서 자동 결제는 개방과 폐쇄의 문제가 아닙니다. 전부 막으면 에이전트는 현실 업무의 문턱에서 멈추고, 전부 열면 조직은 비용과 보안의 장부를 잃습니다. 핵심은 어느 업무에 어떤 금액의 자율성을 줄 것인가입니다. 에이전트에게 필요한 것은 무제한 법인카드가 아니라, 업무 목적에 맞춰 발급되고 만료되는 작은 지출 봉투입니다.

## ▸ 한국 대기업의 사무실에서 이 변화를 읽는 법

한국 대기업에서 이 이슈는 생각보다 현실적입니다. 지금은 많은 AI PoC가 내부 문서 검색, 회의록 요약, 보고서 초안 작성에 머물러 있습니다. 그러나 에이전트가 실제 프로세스 안으로 들어가면 외부 유료 서비스 호출은 피하기 어려워집니다. 시장 조사, 신용 조회, 번역 API, 법률·특허 데이터베이스, 물류 운임 조회, 보안 평판 API처럼 업무 판단에 필요한 정보는 이미 종량제 비용 구조 위에 놓여 있는 경우가 많습니다.

AX 관점에서 첫 번째 질문은 “에이전트에게 결제를 허용할 것인가”가 아닙니다. “어떤 업무 단위가 결제 가능한 업무인가”입니다. 예를 들어 영업 리드 검증 에이전트, 공급망 리스크 모니터링 에이전트, 보안 이벤트 분석 에이전트는 각각 필요한 외부 서비스와 한도가 다릅니다. 한 에이전트가 모든 결제 권한을 갖는 구조보다, 업무별로 수신자와 예산과 만료 시간을 다르게 갖는 구조가 더 현실적입니다.

두 번째 질문은 비용 배부입니다. 사람의 법인카드에는 부서와 프로젝트 코드가 붙습니다. 에이전트의 호출 비용도 마찬가지여야 합니다. 어떤 에이전트가 어떤 API를 몇 번 호출했고, 어떤 업무 산출물을 만들기 위해 얼마를 썼는지 남지 않으면 AX는 곧 비용 불투명성으로 공격받습니다. 자동화 성과를 말하려면 절감된 시간뿐 아니라 새로 발생한 외부 호출 비용도 함께 보여줘야 합니다.

세 번째 질문은 승인선입니다. 모든 결제를 사람이 실시간 승인하면 에이전트의 장점이 사라집니다. 그렇다고 모든 결제를 사전 승인으로 열어둘 수도 없습니다. 그래서 대기업에서는 금액, 데이터 민감도, 외부 전송 여부, 업무 중요도에 따라 자동 승인과 사후 감사와 사람 승인 지점을 나눠야 합니다. 이것은 기술 설정이면서 동시에 회계, 보안, 구매, 현업이 함께 정해야 하는 운영 규칙입니다.

## ▸ 다시 법인카드 앞에서 묻게 되는 것

처음의 법인카드 장면으로 돌아가 봅니다. 조직이 직원에게 카드를 주는 이유는 모든 지출을 믿어서가 아닙니다. 매번 모든 일을 멈춰 세우지 않기 위해서입니다. 대신 한도, 항목, 증빙, 결재, 감사라는 장치를 둡니다. 신뢰는 감정이 아니라 절차로 만들어집니다.

AI 에이전트에게도 같은 일이 벌어지고 있습니다. 에이전트가 업무를 끝까지 수행하려면 언젠가 외부의 유료 문을 만나게 됩니다. 그 문 앞에서 매번 사람을 부를 것인지, 아니면 작은 한도와 명확한 로그를 가진 통행증을 줄 것인지 결정해야 합니다. 중요한 것은 에이전트가 돈을 쓸 수 있다는 사실 자체가 아닙니다. 돈을 쓰는 권한을 어떤 업무 언어로 쪼개고, 어떤 장부에 남기고, 언제 회수할 것인가입니다.

결국 AX의 다음 질문은 “AI가 결제할 수 있는가”가 아니라 “우리 조직은 AI에게 맡길 수 있는 예산의 경계를 이미 그려두었는가”일지도 모릅니다.
