회사에서 가장 평범하지만 강력한 도구 중 하나는 알람입니다.

캘린더 알림은 회의실을 열고, 메신저 알림은 누군가의 업무 순서를 바꾸며, 결재 알림은 멈춰 있던 문서를 다시 움직입니다. 알람은 일을 직접 하지는 않습니다. 하지만 언제 일이 시작되어야 하는지, 누구에게 넘어가야 하는지, 어느 순간 멈춰야 하는지를 알려줍니다. 사무실의 많은 일은 결국 사람의 머릿속 기억보다 이런 작은 시간표와 규칙 위에서 굴러갑니다.

AI 에이전트도 비슷한 길을 걷고 있습니다. 처음에는 “무엇을 할 수 있나”가 관심사였습니다. 파일을 읽을 수 있는지, 웹을 검색할 수 있는지, 코드를 실행할 수 있는지, 보고서를 써줄 수 있는지가 질문이었습니다. 그런데 에이전트가 실제 업무 가까이 들어오면 질문이 바뀝니다. 이제 중요한 것은 “언제 실행되는가”, “얼마나 써도 되는가”, “실행 전후에 무엇을 검사하는가”입니다.

2026년 7월 31일 수집 리포트는 GCN 보도를 인용해 Google이 Gemini API Managed Agents에 몇 가지 운영 기능을 추가했다고 정리했습니다. 보도 기준으로 핵심은 Gemini 3.6 Flash의 기본 적용, environment hooks, token budget cap, scheduled execution trigger, free tier access입니다. 이 글은 GCN 기사와 수집 리포트에서 확인된 범위 안에서 해석합니다. Google의 내부 로드맵이나 모든 고객 적용 상태까지 독립 검증한 글은 아닙니다.

흥미로운 것은 모델 이름보다 주변 장치입니다. 더 빠른 모델도 중요하지만, 에이전트가 회사 업무 안에서 살아남으려면 알람시계, 계량기, 출입문, 작업 전후 점검표가 필요합니다. 이번 소식은 AI 에이전트가 데모 화면을 벗어나 운영 가능한 업무 단위로 바뀌는 장면처럼 보입니다.

## ▸ 새 모델보다 눈에 띄는 것은 손잡이들이다 : Managed Agents 업데이트의 신호

GCN 보도에 따르면 Google은 7월 28일 Gemini API Managed Agents 플랫폼을 확장하며 생산 배포를 겨냥한 통제 기능들을 추가했습니다. Gemini 3.6 Flash가 기본 모델이 되었고, 기존 사용자는 코드 변경 없이 Antigravity preview agent에서 이를 쓰게 된다고 설명했습니다. 개발자는 에이전트 설정에서 다른 지원 모델을 선택할 수도 있다고 합니다.

하지만 AX 관점에서 더 중요한 대목은 모델 교체보다 운영 손잡이입니다. environment hooks는 에이전트 실행 전후에 특정 처리를 붙일 수 있게 합니다. token budget cap은 한 번의 작업이나 일정 기간 동안 에이전트가 소비할 수 있는 토큰 범위를 제한하는 장치로 읽힙니다. scheduled execution trigger는 사람이 매번 버튼을 누르지 않아도 정해진 시간에 에이전트가 움직일 수 있게 하는 기능입니다.

또 보도는 이 기능들이 2026년 7월 7일 공개된 장기 백그라운드 작업 지원과 원격 MCP 서버 연동 위에 더해졌다고 설명했습니다. post-execution hook 요청은 Google의 egress proxy를 지나며, 목적지는 환경 allowlist에 있어야 하고 인증 토큰은 hook 파일이 아니라 네트워크 설정에 둔다는 설명도 포함되어 있습니다. 말하자면 에이전트의 손발이 길어지는 만큼, 손발이 닿을 수 있는 범위도 함께 좁히려는 설계입니다.

## ▸ 실험용 스크립트와 운영 시스템을 가르는 것은 기억이 아니라 경계다

많은 조직에서 AI 에이전트 PoC는 작은 스크립트로 시작합니다. 특정 폴더를 읽고, 요약을 만들고, 메일 초안을 쓰고, 대시보드 값을 가져옵니다. 처음에는 “된다”는 사실이 중요합니다. 그런데 몇 번 성공한 뒤 같은 에이전트를 매주, 매일, 여러 부서에서 쓰기 시작하면 전혀 다른 문제가 나타납니다.

첫 번째는 비용입니다. 사람이 한 번 질문하는 챗봇과, 정해진 시간마다 여러 시스템을 조회하는 에이전트의 비용 구조는 다릅니다. 에이전트가 실패 후 재시도하거나, 너무 넓은 문서를 읽거나, 불필요한 도구 호출을 반복하면 토큰 사용량은 업무량보다 빠르게 커질 수 있습니다. token cap은 단순한 절약 기능이 아니라 자동화의 폭주를 막는 계량기에 가깝습니다.

두 번째는 권한입니다. 에이전트가 MCP 서버나 외부 API를 통해 업무 시스템에 붙으면, 모델이 무엇을 아는가보다 에이전트가 어디까지 갈 수 있는가가 중요해집니다. allowlist, egress proxy, 토큰 분리 같은 장치는 화려해 보이지 않습니다. 그러나 대기업 업무에서는 이런 보이지 않는 경계가 실제 도입 여부를 결정합니다.

세 번째는 시간입니다. scheduled trigger가 붙으면 에이전트는 사용자의 요청을 기다리는 도구에서 정해진 리듬으로 움직이는 업무 프로세스가 됩니다. 매일 아침 매출 이상치를 찾고, 매주 금요일 리스크 신호를 요약하고, 월말에 비용 데이터를 모으는 식입니다. 이때 에이전트는 채팅창보다 배치 작업과 더 닮아갑니다.

## ▸ 자동화인가 통제인가 : 같은 운영 기능의 두 얼굴

이 변화는 분명 반가운 방향입니다. 업무 자동화가 매번 수동 실행에 의존하면 확장성이 낮습니다. 실행 전후 훅이 있으면 데이터 검증, 로그 기록, 승인 요청, 후속 알림을 붙일 수 있습니다. 토큰 한도가 있으면 비용 예측 가능성이 높아집니다. 예약 실행은 반복 보고와 모니터링 업무를 사람의 기억에서 시스템의 시간표로 옮깁니다.

하지만 운영 기능이 늘어난다는 것은 동시에 플랫폼 의존이 깊어진다는 뜻이기도 합니다. 에이전트의 실행 방식, 비용 제어, 네트워크 경계, 인증 토큰 관리가 특정 클라우드의 관리 계층 안으로 들어가면 기업은 편리함과 종속을 함께 받아들입니다. 직접 만들면 복잡하지만 통제권이 넓고, 관리형 플랫폼을 쓰면 빠르지만 운영 규칙이 플랫폼의 언어에 맞춰집니다.

또 하나의 위험은 통제가 있다고 해서 업무 책임이 사라진다고 착각하는 것입니다. 토큰 cap이 있어도 잘못된 데이터를 읽으면 잘못된 결론을 냅니다. scheduled trigger가 있어도 휴일, 조직개편, 예외 계약처럼 사람의 맥락이 필요한 경우는 남습니다. hooks가 있어도 무엇을 검사할지 설계하지 않으면 빈 통로만 하나 더 생깁니다.

그래서 이번 업데이트를 “에이전트가 더 똑똑해졌다”로만 읽으면 절반만 보는 셈입니다. 더 정확한 해석은 “에이전트가 회사 시스템 안에서 오래 돌기 위해 필요한 운영 장치들이 제품의 중심으로 올라오고 있다”는 것입니다.

## ▸ 한국의 사무실에서 이 변화를 읽는 법

한국 대기업에서 에이전트를 도입할 때 가장 먼저 부딪히는 것은 모델 성능표가 아닙니다. 데이터 권한, 보안 심의, SaaS 조달, 비용 배부, 운영 책임자 지정입니다. 현업은 “매일 아침 이 자료를 정리해 달라”고 말하지만, IT와 보안 조직은 “어떤 시스템을 읽고, 어떤 계정으로 접속하며, 실패하면 누가 확인하는가”를 묻습니다.

Managed Agents류 플랫폼의 의미는 여기에서 생깁니다. environment hook은 결재 전 검증 단계처럼 쓸 수 있습니다. 예를 들어 영업 리포트 에이전트가 실행되기 전에는 접근 가능한 고객군을 확인하고, 실행 후에는 원본 데이터 링크와 생성 로그를 남기도록 설계할 수 있습니다. token cap은 부서별 AI 예산을 업무 단위로 배부하는 기준이 될 수 있습니다. scheduled trigger는 “누군가 매주 수동으로 돌리는 엑셀 매크로”를 공식 업무 스케줄로 바꾸는 출발점이 됩니다.

다만 도입의 순서는 조심스러워야 합니다. 전사 범용 에이전트를 한 번에 여는 것보다, 반복 주기가 분명하고 데이터 경계가 좁고 실패 시 영향이 제한적인 업무부터 시작하는 편이 안전합니다. 주간 시장 모니터링, 내부 FAQ 갱신, 비용 이상치 탐지, 회의 후속 과제 정리처럼 실행 조건과 검토자가 명확한 업무가 먼저입니다.

AX 담당자에게 필요한 질문도 달라집니다. “어떤 모델이 가장 좋은가”보다 “이 에이전트가 언제 시작되고, 어디까지 접근하고, 얼마를 쓰고, 어떤 로그를 남기며, 언제 사람에게 멈춰 서는가”를 물어야 합니다. 자동화는 사람을 없애는 기술이 아니라, 사람이 매번 기억하던 업무의 리듬과 경계를 시스템 안에 새기는 일에 가깝습니다.

## ▸ 결국 알람은 일을 대신하지 않고 일을 시작하게 한다

다시 사무실의 알람으로 돌아가 봅니다. 캘린더 알림은 회의를 대신하지 않습니다. 결재 알림은 판단을 대신하지 않습니다. 하지만 알람이 없으면 많은 일은 늦어지고, 잊히고, 누군가의 개인 기억에 묶입니다. 좋은 알람은 사람을 재촉하는 소음이 아니라 업무가 움직일 때와 멈출 때를 알려주는 약속입니다.

AI 에이전트도 이제 그런 약속을 필요로 합니다. 모델이 더 빠르고 똑똑해지는 것만으로는 충분하지 않습니다. 회사 안에서 오래 쓰이는 에이전트는 시간표, 비용 한도, 접근 경계, 실행 전후 점검을 가져야 합니다. GCN이 전한 Gemini API Managed Agents 업데이트는 바로 그 방향을 보여주는 작은 신호입니다.

에이전트가 스스로 움직이는 시대에, 우리 회사는 먼저 무엇을 정해야 할까요. 더 똑똑한 심부름꾼을 고르는 일일까요, 아니면 그 심부름꾼이 언제 어디까지 움직여도 되는지를 정하는 일일까요.
