회의실 책상 위에 보고서가 한 묶음 올라옵니다. 누군가 밤새 문서에 빨간펜을 그어 놓았습니다. 오탈자, 표현 오류, 숫자 불일치, 근거 부족, 빠진 첨부파일까지 표시가 빽빽합니다. 처음에는 고맙습니다. 놓칠 뻔한 문제를 대신 찾아줬으니까요.

그런데 종이가 계속 쌓이면 이야기가 달라집니다. 빨간펜이 많아질수록 문서가 좋아지는 것이 아니라, 문서를 고칠 사람이 부족해집니다. 어떤 표시는 정말 치명적인 오류이고, 어떤 표시는 문맥상 문제가 없고, 어떤 표시는 고치면 오히려 다른 문단을 망가뜨립니다. 결국 회의실의 병목은 “누가 오류를 찾았는가”가 아니라 “누가 이 표시들을 판단하고 고칠 것인가”로 옮겨갑니다.

보안 업무에서도 비슷한 장면이 벌어지고 있습니다. 2026년 8월 5일 수집 리포트는 ZDNET의 8월 4일 기사, “AI is finding bugs faster than humans can fix them”을 주요 뉴스로 정리했습니다. ZDNET은 AI가 보안 취약점을 더 빠르게 찾아내는 동시에, 기업 보안팀이 그것을 분류하고 수정하고 검증하는 속도는 따라가지 못하고 있다고 지적했습니다. 이 글은 해당 기사와 수집 리포트에서 확인한 범위에 기대어 씁니다.

흥미로운 점은 이 뉴스가 “AI가 보안을 더 잘한다”는 단순한 낙관도, “AI가 위험하다”는 단순한 경고도 아니라는 데 있습니다. AI가 빨간펜을 너무 잘 들기 시작하면서, 조직은 새로운 질문 앞에 섭니다. 자동으로 발견된 문제는 누가 우선순위를 매기고, 누가 고치며, 누가 고친 결과가 안전하다고 확인할 것인가.

## ▸ 탐지기가 빨라질수록 책상 위에는 더 많은 미결함이 쌓인다 : 발견과 처리의 간극

ZDNET 기사에서 가장 중요한 문장은 제목 자체에 가깝습니다. AI가 버그를 찾는 속도는 빨라지고 있지만, 사람이 그것을 고치는 속도는 같은 방식으로 늘지 않습니다. 기사에 따르면 AI 기반 취약점 발견은 보안 보고의 양을 키우고 있고, 기업은 더 빠른 탐지를 원하면서도 동시에 더 적은 소음을 필요로 하는 모순적인 상황에 놓입니다.

취약점은 발견되는 순간 바로 해결되는 것이 아닙니다. 먼저 그 보고가 실제 문제인지 봐야 합니다. 해당 시스템의 배포 환경에서는 얼마나 위험한지 판단해야 합니다. 다른 보안 장치가 이미 막고 있는지 확인해야 합니다. 고칠 수 있다면 어느 팀이 수정할지 정해야 하고, 수정 후에는 테스트와 재검증을 거쳐야 합니다. 즉 취약점 하나는 단순한 알림이 아니라 작은 업무 티켓입니다.

문제는 AI가 이 티켓을 대량으로 만들 수 있다는 점입니다. 이전에는 사람이 며칠에 걸쳐 찾던 문제를 도구가 몇 시간 안에 찾아낼 수 있습니다. 겉으로 보면 좋은 일입니다. 숨어 있던 위험이 더 빨리 드러나기 때문입니다. 그러나 티켓을 처리하는 조직의 용량이 그대로라면, 더 빠른 발견은 더 빠른 해결이 아니라 더 긴 대기열을 만들 수 있습니다.

ZDNET은 Google Chrome의 사례와 Apple의 보안 보고 처리 부담을 언급하며, 대형 기술기업조차 AI가 늘린 취약점 보고 흐름을 감당해야 하는 압박을 받고 있다고 설명합니다. 이 대목에서 우리가 읽어야 할 것은 특정 회사의 어려움보다 구조입니다. AI가 만든 생산성은 한 업무 단계에서만 증가할 때, 다음 단계의 병목을 더 선명하게 드러냅니다.

## ▸ 진짜 병목은 스캐너가 아니라 수정과 검증의 결재선이다

보안 자동화를 도입할 때 조직은 흔히 탐지율을 먼저 봅니다. 더 많은 취약점을 찾는가. 더 빨리 경고하는가. 더 정확히 분류하는가. 물론 중요합니다. 그러나 실무에서 더 어려운 곳은 탐지 다음입니다. 고칠 것인가, 미룰 것인가, 우회 조치할 것인가, 배포를 멈출 것인가, 어느 릴리즈에 포함할 것인가.

이 판단은 단순한 기술 문제가 아닙니다. 운영 중인 서비스의 안정성, 고객 영향, 개발 일정, 규제 요구, 내부 감사, 장애 대응 체계가 함께 걸립니다. 작은 라이브러리 업데이트처럼 보였던 수정이 결제 시스템의 예외 처리를 건드릴 수 있고, 인증 로직의 패치는 고객 로그인 실패로 이어질 수 있습니다. 그래서 보안팀은 “위험하니 고치자”고 말하고, 개발팀은 “어떻게 안전하게 고칠 것인가”를 묻고, 운영팀은 “언제 배포할 수 있는가”를 따집니다.

ZDNET 기사도 AI가 직접 버그를 고치는 일의 한계를 강조합니다. 기사에 인용된 연구에 따르면 2만 건 이상의 이슈를 대상으로 살펴봤을 때 LLM은 개발자보다 새 취약점을 거의 9배 더 많이 만들 수 있다는 결과가 언급됩니다. 또한 Python 코드 자동 패치 도구인 PatchitPy 같은 사례도 성공률이 80% 수준으로 소개되지만, 기사 표현처럼 이는 의미 있는 성과이면서도 완전한 해결책은 아닙니다.

이 지점이 중요합니다. AI는 수정 초안을 만들 수 있습니다. 관련 코드를 찾아주고, 의존성 업데이트 방향을 제안하고, 테스트 케이스를 떠올리게 할 수 있습니다. 하지만 “이 변경이 우리 시스템의 업무 규칙과 보안 경계를 깨지 않는가”라는 질문은 여전히 조직의 책임입니다. 빨간펜이 문장을 고쳐주더라도 최종 결재는 작성자와 승인자의 몫인 것처럼, 보안 패치의 책임은 도구가 아니라 운영 체계에 남습니다.

## ▸ 자동화인가, 업무 부채의 증폭인가 : 같은 AI 보안 도구의 두 얼굴

AI 기반 취약점 탐지는 분명 큰 기회입니다. 사람이 놓치던 패턴을 더 빨리 찾고, 오래된 코드베이스의 위험 신호를 드러내며, 보안팀이 반복 검토에 쓰던 시간을 줄여줄 수 있습니다. 특히 대규모 시스템을 운영하는 기업에서는 모든 저장소와 모든 의존성을 사람이 직접 훑는 일이 사실상 불가능합니다. AI는 이 넓은 표면을 빠르게 스캔하는 도구가 될 수 있습니다.

하지만 같은 도구가 업무 부채를 증폭할 수도 있습니다. 중요하지 않은 알림이 너무 많아지면 보안팀은 경고를 믿지 않게 됩니다. 반대로 모든 알림을 긴급으로 취급하면 실제 고위험 취약점의 처리 시간이 늦어집니다. 자동 생성된 패치가 충분한 검증 없이 들어가면, 취약점을 줄이려던 작업이 새로운 취약점을 만들 수도 있습니다.

그래서 이 변화는 보안팀을 대체하는 이야기가 아닙니다. 오히려 보안팀의 역할을 바꿉니다. 과거에는 취약점을 찾는 능력이 중심이었다면, 앞으로는 위험을 선별하고, 수정 흐름을 설계하고, 자동화된 제안의 품질을 검증하는 능력이 더 중요해집니다. 빨간펜을 직접 긋는 사람에서, 빨간펜이 만든 업무 흐름을 통제하는 사람으로 이동하는 셈입니다.

ZDNET 기사에서 제안되는 방향도 이와 맞닿아 있습니다. 모델에게 “취약점을 없애라” 같은 넓은 지시를 주기보다 특정 upstream fix를 반영하거나 특정 의존성을 업데이트하는 식으로 범위를 좁히라는 조언, 수정과 검증을 분리하라는 조언, 인증·권한·데이터 처리처럼 복잡한 변경은 인간 엔지니어가 책임져야 한다는 조언이 나옵니다. 이는 기술 팁처럼 보이지만 사실은 업무 설계 원칙에 가깝습니다.

## ▸ 한국 대기업의 사무실에서 이 변화를 읽는 법

한국 대기업에서 보안 AX나 개발 자동화를 추진한다면 이 뉴스는 꽤 현실적인 경고입니다. 많은 조직이 코드 분석 도구, SAST, DAST, 오픈소스 취약점 점검, AI 코드 리뷰, 자동 PR 생성 도구를 동시에 검토합니다. 각각은 생산성을 높인다고 말합니다. 그러나 도입 후 실제 현업이 마주하는 것은 대시보드의 예쁜 그래프가 아니라 Jira 티켓, 보안 예외 신청, 배포 승인, 장애 리스크 회의입니다.

AX 관점에서 핵심은 “AI가 몇 건을 찾아냈는가”가 아닙니다. 찾아낸 항목 중 어느 것이 실제 업무 위험인지, 누가 고칠지, 어느 릴리즈에 넣을지, 검증 증거를 어디에 남길지, 실패하면 어떻게 롤백할지입니다. 보안 자동화는 탐지 도구 구매로 끝나지 않고 결재선과 책임선을 다시 그리는 일입니다.

특히 대기업에서는 권한과 데이터 경계가 복잡합니다. 어떤 코드는 외주사와 함께 관리되고, 어떤 시스템은 망분리 환경에 있고, 어떤 업무는 규제 감사 대상입니다. AI가 취약점 보고서를 만들거나 수정 PR을 제안할 때도, 그 제안이 접근 가능한 코드와 로그, 테스트 환경, 승인 권한 안에서만 움직이도록 설계해야 합니다. AI 에이전트에게 저장소 접근권한을 주는 순간, 그것은 단순한 개발 도구가 아니라 업무 시스템에 들어온 행위자가 됩니다.

따라서 보안 AX의 첫 설계 문서는 기능 목록보다 흐름표에 가까워야 합니다. 탐지, 분류, 담당자 배정, 수정 초안, 코드 리뷰, 테스트, 보안 재검증, 배포 승인, 롤백, 감사 로그가 한 줄로 이어져야 합니다. 자동화할 단계와 사람이 승인할 단계를 구분해야 합니다. 모든 취약점을 같은 강도로 다루는 것이 아니라, 업무 영향도와 노출 범위, 데이터 민감도에 따라 다른 길을 태워야 합니다.

이런 관점에서 AI 보안 도구는 빨리 도입할수록 좋은 물건이라기보다, 업무 흐름이 준비된 조직에서 더 큰 효과를 내는 도구입니다. 빨간펜을 많이 사는 것보다 중요한 것은, 빨간펜이 표시한 문서를 누가 언제 어떤 기준으로 고칠지 정하는 일입니다.

## ▸ 다시 빨간펜이 놓인 회의실로

처음 장면으로 돌아가 봅니다. 회의실 책상 위에는 여전히 빨간펜 표시가 가득한 보고서가 놓여 있습니다. 예전보다 더 많은 오류가 보입니다. 보이지 않던 문제가 드러났다는 점에서 이것은 진전입니다. 하지만 그 표시들이 자동으로 좋은 문서를 만들지는 않습니다.

AI가 보안 취약점을 더 빨리 찾아내는 시대도 마찬가지입니다. 발견은 시작일 뿐입니다. 기업의 실력은 탐지 알림의 숫자가 아니라, 그 알림을 업무 흐름 안에서 판단하고 고치고 검증하는 속도와 질에서 드러납니다.

앞으로 보안 AX의 질문은 “AI가 얼마나 많은 버그를 찾았는가”가 아니라 이렇게 바뀔지 모릅니다. 우리 조직은 AI가 찾아낸 빨간펜을 실제 수정 가능한 업무로 바꿀 준비가 되어 있는가.
